Build Plan

Ten phases, roughly sixteen weeks of focused solo work. The ordering is not by architectural layer but by what could still prove the design wrong — the cheapest experiments that could invalidate a decision come first, and nothing large gets built on an assumption that has not been tested.

Risk-first ordering Walking skeleton before depth Every phase ends in a demo Design frozen 15 Sep

How this is ordered, and why

Risk first. The single largest design risk is not the supervisor or the database — it is whether one manifest schema can express four genuinely different studios without a special case. h3 and iris are Go wrapping hand-written Metal C; ltx is Python on MLX; AuK is Python on PyTorch with a FastAPI server. If the schema cannot describe all four, the "adding a studio is a data change" principle collapses and much of the rest follows it. That test costs two days and no code, so it goes first.

Walking skeleton before depth. Phase 1 builds a thin end-to-end path — load a manifest, spawn a process, watch it, stop it — with a deliberately ugly HTML page. Nothing is polished until something works end to end, because the gaps between components are where designs actually fail, not inside them.

One real studio at a time. h3 studio carries phases 1 through 3 alone. A second caller arrives only in phase 4, which is the point at which interfaces stop being a refactor of one studio and become interfaces. Building the SDK against two callers before either works would be designing in the dark.

Every phase ends in something you can show. If a phase has no demo, it has no definition of done, and a solo project with no definition of done drifts.

The map

Phases are strictly sequential because each one's demo depends on the last. The two dashed tracks run from day one alongside everything.

Phase 0 · Prove the manifest

P0

Four manifests, no daemon

2–3 days
  • Write the JSON Schema for the manifest, including processes[], runtime, weights[], storage, capabilities, sdk, test.
  • Hand-write helmstudio.yaml for all four studios against the real repositories — not sketches, the actual build steps and run commands you would type.
  • Build helm validate as a standalone binary. It is the first thing that compiles and the last thing you will stop using.
  • Write the OpenAPI document's outline — endpoint names and shapes only, no schemas yet — so phase 3 starts from a sketch rather than a blank file.
The test that matters

If any of the four needs a field the schema does not have, add it now — that is the phase working. If any needs a special case in Go, the schema is wrong and this is the cheapest possible moment to find out.

Phase 1 · Supervision — the walking skeleton

P1

Spawn, watch, stop, re-adopt

8–10 days
  • Repo and skeleton: monorepo layout, cmd/helmstudio, internal/…, and the platform package with its four seams — process group control, secret store, app paths, reveal-in-file-manager — darwin implementations only, but the interfaces defined.
  • Directories helper before anything writes a file. Retrofitting paths is miserable.
  • Store: SQLite open with the WAL pragmas, migration runner on user_version, schema v1 covering installations, step_runs, processes, jobs, log_files, settings.
  • Manifest loader with the three-source resolution, reading from local_path for now.
  • Supervisor: port allocator, template substitution, spawn with Setpgid, health polling against a real budget, group start ordering, reverse teardown, and the re-adoption check on pid + start time + pgid.
  • Logs as append-only files with an index row, streamed over SSE.
  • A deliberately ugly HTML page that lists studios and has Launch and Stop. No design system. Resist.
Demo

Launch h3 studio from a local checkout, generate a video in its own UI, kill -9 the daemon, restart it, and watch the running studio be re-adopted rather than orphaned. Then stop it and confirm no process survives.

Phase 2 · Install and weights

P2

From a URL to a generated video on a clean machine

8–10 days
  • Clone with submodules at a pinned ref; ordered build steps with streamed output; resume from the first step that has not succeeded; cancel via process-group kill.
  • Tool probing from requires.tools, failing fast with the command that installs the missing one.
  • Hugging Face downloader: file listing, range resume from .part length, re-resolution of signed URLs on every resume, 429 backoff, auth_required on 401/403, Keychain for the token.
  • Linked weights — point at an existing directory, symlink into the cache, read-only, missing when the volume goes. Build this alongside downloading, not after; they share one resolution path.
  • Disk pre-check with real numbers; the cache view with reference counts and reclaim that never follows a symlink.
Demo

A machine that has never seen the repo goes from listed to a generated video. Interrupt the build once and resume. Then install a second time using a model directory you already had, and watch nothing download.

Phase 3 · The contract and the runtime SDK

P3

One document, two providers, one suite

10–12 days
  • Finish the OpenAPI document first. Everything downstream is generated from it, so a day spent here is worth a week later.
  • Schema v2: sessions, kv, records, assets, derived, items, item_inputs, tags, items_fts, inbox.
  • Endpoints, in this order: /me, /kv, /sessions, /assets and :adopt, /gallery, /records, /jobs, /events, /handoff.
  • Capability-scoped per-launch tokens injected at spawn.
  • Media engine v1: probe, thumbnail, poster, waveform, h264 proxy — all as derived files.
  • Generate the Go and Python clients; write the embedded provider as the same code path without HTTP; ship helm dev as the daemon in single-studio mode.
  • The conformance suite, run twice in CI. Write it as you write endpoints, not afterwards.
  • helmstudio fsck, while the asset rules are fresh.
Demo

h3 studio records its takes through the SDK; the launcher shows them with thumbnails and provenance; conformance is green against both the daemon and the embedded provider; helm dev runs the studio with no daemon installed.

Phase 4 · The second and third callers

P4

ltx studio and AuK studio

6–8 days
  • python.version handling, per-studio uv environments, the bash web/run.sh run shape.
  • The Python runtime SDK against a real caller.
  • The one-heavy-studio rule with the switch confirmation, now that two studios can actually compete for memory.
  • Expect schema churn here and treat it as success: this is the phase that tells you which parts of phase 0's manifest were guesses.
Demo

Three studios installed side by side with independent environments; AuK generates speech through the SDK into the shared gallery; switching from ltx to h3 shows the memory arithmetic and stops the first cleanly.

Phase 5 · Design system and packages

P5

It stops looking like a prototype

10–12 days
  • helm-css in five layers, with visual regression in CI on both themes and a contrast check on every token pair.
  • The real launcher: catalogue, studio detail with the install checklist and terminal, process group, launching and switch dialog, gallery, models and disk, settings, doctor.
  • helm-ui-sdk: helm-terminal first (virtualised ring buffer, ANSI, carriage returns), then helm-gallery, then helm-player with frame extraction.
  • Theme push over SSE so toggling the launcher re-themes running studios.
Demo

h3 studio's hand-built take list replaced by <helm-gallery> in an afternoon, and its log panel by <helm-terminal>; toggle the theme in the launcher and every open studio follows.

Phase 6 · The library and iris studio

P6

Anyone can add a studio

6–8 days
  • iris studio: selectable weights and the pre-launch checkpoint picker.
  • Manifest library: three sources, local override with Revert, duplicate-and-edit.
  • The in-app editor with live validation and criteria scoring; import (drop, pick, paste, URL) and export.
  • The certification checks and the add-a-studio approval screen, with every build command shown verbatim.
  • helm studio init, helm test, helm doctor --studio.
Demo

Take a repository that has never heard of helmstudio, write its manifest in the app, test it without installing, install it, then export the file as a pull request to that repo.

Phase 7 · Timeline and export

P7

The part that will be wrong twice

10–12 days
  • Timeline document and rows; the editor component with drag, trim and snapping; gapless preview across cuts.
  • Export as a Job: conform-to-target filter graph, and the stream-copy fast path when everything already matches.
  • Golden frame-hash tests across both providers — this is what stops the media engine forking.
  • Bundle a pinned LGPL ffmpeg with videotoolbox. Settle the licensing question before this phase, not during it.
Demo

A fourteen-second sequence assembled from three studios with an AuK voice line, exported and appearing in the gallery with its clips as inputs — and the stream-copy case verified bit-identical to its source.

Phase 8 · The Mac app and first release

P8

Something a stranger can install

7–9 days
  • Electron shell: sidecar spawn with the stdout handshake, adoption of an existing daemon, quit behaviour and the keep-running-in-menu-bar choice.
  • Native affordances: folder picker, Reveal in Finder, menu bar item, notifications, Dock progress.
  • Browser-path auth: the one-time token URL and the SameSite=Strict cookie, plus Host and Origin checks.
  • Signing, notarisation of the bundle and the nested Go binary, electron-updater against GitHub Releases, and the Homebrew formula.
Demo

A notarised .dmg on a Mac that has never run helmstudio: double-click, install a studio, generate something, quit the app with the studio still alive in the menu bar, then take an update that ships a fifth studio pointer.

Phase 9 · SDK documentation and helmstudio.in

P9

The two things that decide whether anyone else shows up

8–10 days

Deliberately last. An API you are still changing cannot be documented without documenting it twice, screenshots of a half-built UI age in days, and a quickstart is only worth writing once it can be run against a shipping binary. Everything here is assembly rather than authorship — if the tracks below have been kept, most of the content already exists.

The SDK documentation

  • Quickstart — from nothing to a scaffolded studio recording its first gallery item, tested end to end against the released binaries on a clean machine. If it takes more than ten minutes, fix the tooling rather than the prose.
  • Concepts — the manifest, process groups, weights managed and linked, capabilities, the two providers, and why a studio stays an independent repo.
  • Guides — wrap a model repo that has no manifest; record outputs with provenance; use sessions; hand off to the timeline; theme with helm-css; develop and test in isolation.
  • Generated reference — the API pages from the OpenAPI document and the manifest pages from the JSON Schema. Generated, never hand-written, so reference material cannot drift from the thing it describes. This is the same rule that governs the three SDK clients.
  • CLI reference for init, dev, validate, test, doctor, adopt.
  • Publishing — the fifteen criteria, the certification levels, and what a registry pull request actually contains.
  • Worked examples — the four launch manifests annotated line by line. These already exist from phase 0 and are the most useful page on the site.

The website

  • What helmstudio is, in a sentence that names the problem: open-weight video, image and speech models on your own machine, without the afternoon of setup.
  • The problem made concrete — the submodule you did not clone, the Python version mismatch, the 60 GB download with no resume, the two studios that both want port 8720.
  • The launch studios with their runtime badges, so a visitor can tell at a glance what will run on their hardware.
  • A real screen recording of an install and a generation. This is the single highest-value asset on the site and the reason it cannot be made earlier.
  • Install, honestly stated: Homebrew formula and the notarised .dmg, with the current platform support named rather than implied.
  • A short "add your own studio" section pointing at the docs, and the repository.
  • No signup, no waitlist, no pricing. It is a local open-source tool and the site should read like one.

Both sites are built with helm-css, which is worth doing for its own sake: a design system that works outside the application it was drawn for is a design system, and one that does not is a stylesheet. Static output, deployed to helmstudio.in with the documentation at /docs, and the reference pages regenerated in CI so a merged API change updates them without anyone remembering to.

Demo

Hand the quickstart to someone who has never seen the project, on a Mac that has never run it, and watch them reach a generated output without asking you anything. That is the only test of documentation that means anything.

Day 1Manifest JSON Schema. Write h3's manifest first — you know that repo best — then iris, since it is the closest sibling.
Day 2ltx and AuK manifests. These are where the schema will bend; note every field you wished existed rather than working around it.
Day 3helm validate compiling and passing on all four. OpenAPI outline. Open the /healthz PR on h3 studio.
Day 4Repo skeleton, platform package interfaces, directories helper, SQLite open with pragmas, migration runner.
Day 5Schema v1 and its store methods. CI green on build, test and helm validate, on macOS and Linux both.

By the end of week one nothing generates anything, and that is correct. What you have instead is the answer to the only question that could have forced a redesign, plus the scaffolding that everything else sits on.

The honest caveat on the estimate

Sixteen weeks assumes focused days and no long detour. Two phases carry most of the schedule risk: phase 3, because an API you will live with for years deserves more care than a plan admits, and phase 7, because conform-and-concat is always wrong twice before it is right. If something has to give, cut scope inside phases 6 and 7 rather than compressing phase 3 — a rushed contract is paid for every week afterwards. Phase 9 is the one place where shipping less is genuinely fine: a quickstart, the generated reference and the four annotated manifests are worth more than a complete site, and the rest can follow.

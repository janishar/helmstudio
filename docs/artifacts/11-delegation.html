Running the build with agents

Agents are good at work that has a written contract, a mechanical way to tell right from wrong, and a bounded surface. That is not a limitation to work around — it is the shape the build plan already has, because the same properties that make a design implementable make it delegable. This plan turns the ten phases into agent-shaped units and names the places where they are not.

1 · What makes a task agent-shaped

Three properties, and a task needs all three. A written contract — an OpenAPI document, a JSON Schema, a state table, a token file — so correctness is a question with an answer rather than a matter of taste. A mechanical verification — a test that fails, a schema that rejects, a diff that is non-empty — because an agent optimises for the check you give it, and if the check is "looks right" you will get code that looks right. A bounded surface — named files it may touch and named files it may not — because the failure mode of a capable agent is not incompetence, it is scope creep that quietly breaks something three directories away.

This reframes why phase 0 matters.

The manifest schema, the OpenAPI document, the conformance suite and the golden export tests were already the right engineering. Under agent execution they become something more: they are the substrate that makes delegation safe. Every hour spent making a contract machine-checkable buys back a day of reviewing plausible-looking code. Front-load them harder than a human-only plan would.

2 · The constraint that shapes everything

Nothing that touches a model can be verified in the cloud

The product exists to run 20 GB models on Apple Silicon. An agent in a Linux container can write the supervisor, the store, the SDK, the CSS and the docs — it cannot prove that h3 studio actually generated a video, that Metal compiled, or that memory stayed inside budget. Those verifications happen on your Mac, and there is exactly one of it.

So the work splits cleanly in two, and the split should be explicit in every task brief:

Cloud-verifiableMachine-bound
Schema and manifest validation, the store and migrations, the supervisor's logic with fake child processes, the HTTP layer, the SDK clients and their conformance suite, helm-css and visual regression, docs generation, most unit testsAnything that spawns a real studio, builds Metal kernels, downloads weights, loads a model, measures memory, renders with ffmpeg on videotoolbox, or produces a screenshot of a real UI
Parallel — as many agents as you can reviewSerial, one heavy test at a time, which is the same constraint the product itself enforces

The practical consequence is a rhythm rather than a blockage: agents produce cloud-verified work in parallel through the day, and integration against the real hardware happens in one batch you supervise, on your machine, before anything merges.

3 · The loop

Two rules make this work rather than generate churn. An agent never merges its own work — it produces a branch and a report, and the gate decides. And a failure goes back as the failing check, not as a vague instruction: "conformance case etag_conflict_returns_409 fails" is actionable; "this isn't right" produces a rewrite of the wrong thing.

4 · Six roles

Not six agents — six briefs. The same underlying agent behaves differently given a different job description, and keeping them distinct is what stops an implementer quietly rewriting a test to make itself pass.

Contract author

runs rarely · output is a spec, never code

Turns a frozen design section into a machine-checkable artefact: the JSON Schema, the OpenAPI document, a state transition table, the token file. Produces no implementation, which is the point — a spec written by the thing that will implement it has a way of describing what is easy rather than what is right.

Implementer

the workhorse · one bounded slice per run · worktree isolation

Builds one component against a contract that already exists, in files it is told it may touch. Never edits tests it did not write. Never changes a schema — if the contract seems wrong, it stops and says so.

Test author

adversarial · runs before or beside the implementer, never after

Writes the failing tests from the contract, deliberately without reading the implementation. The conformance suite in particular must come from the OpenAPI document and the design docs, because a suite derived from the code proves only that the code does what it does.

Reviewer

reads a diff, produces findings, changes nothing

The role that caught eight blocking issues across the three design documents earlier in this project, and the one that pays the most per token. Give it the diff, the contract and the design section, and ask specifically for contradictions with the frozen design rather than general code quality.

Mechanical

high volume · fully verifiable · low judgement

Token migration across a stylesheet, generated-client regeneration, manifest authoring from a README, docs reference generation, dependency bumps. These are the tasks where agents are unambiguously better than a person, because the verification is exact and the work is tedious.

Explorer

read-only · answers a question, touches nothing

"How does ltx studio decide its output path?" "Which files write outside the checkout?" The h3 dry run was this role. Cheap, safe to run many at once, and the right first move before any brief is written against an unfamiliar repo.

5 · The task brief

Every run uses the same shape. The parts that matter most are the last two, and they are the ones easiest to leave out.

GOAL One sentence. If it needs two, it is two tasks. CONTRACT The frozen artefacts this must satisfy, by path: api/openapi.yaml §/assets · schema/manifest.json · docs/state-tables.md §install TOUCH internal/assets/**, internal/store/assets.go DO NOT api/**, schema/**, test/conformance/**, any other package DONE go test ./internal/assets/... passes test/conformance -run Assets passes against the embedded provider go vet clean · gofmt clean · no new dependency in go.mod OUT OF Thumbnails and proxies (separate task). HTTP handlers (separate task). SCOPE Anything requiring a GPU — leave a failing skipped test and say so. IF THE Stop. Report the contradiction with a quote from the contract and a DESIGN proposed change. Do not improvise a schema field, rename an endpoint, IS WRONG or relax a test to make the build pass.

That last block is the single highest-value paragraph in the brief. A capable agent handed an inconsistent design will resolve it — silently, plausibly, and in a way that diverges from the other four agents resolving the same inconsistency differently. Making escalation the required behaviour turns a design flaw into one question instead of five divergent implementations.

6 · The verification ladder

Each rung is cheaper than the one below it and catches different things. Run them in order and stop at the first failure.

Rungs 1 to 7 should be one command and one CI workflow. If running the gate is more effort than reading the diff, you will stop running it, and the whole model collapses to you reviewing everything by hand.

7 · Phase by phase

P0 · Manifests

4 explorers + 4 mechanical, parallel. One per studio: read the repo, write the manifest. Then you reconcile the four into a schema. Near-ideal agent work.

P1 · Supervision

Mostly you. The walking skeleton is one coherent thing; splitting it creates integration debt. Delegate the store, migrations and the directories helper as separate slices.

P2 · Install & weights

3 parallel slices: git/build runner, HF downloader, linked weights. Each has a clear contract and a testable surface with fakes.

P3 · Contract & SDK

You write the OpenAPI. Then fan out hard: each endpoint group, each generated client, the conformance suite by a separate test author.

P4 · Python studios

Half and half. uv environment handling is agent work; the schema churn it surfaces is your judgement.

P5 · Design & packages

Highly parallel. Each screen, each component, the CSS layers, the h3 token migration — all bounded with visual regression as the gate.

P6 · Library & iris

Parallel. Editor, import/export, criteria checks, approval screen — four independent surfaces over one settled schema.

P7 · Timeline

Least agent-friendly. ffmpeg correctness is empirical and machine-bound. Agents write the golden-test harness; you iterate the filter graph.

P8 · Mac app

Mixed. Electron main process and the handshake delegate well. Signing and notarisation are yours — they need your certificates.

P9 · Docs & site

Most parallel of all. Generated reference is mechanical; each guide is one bounded task against a phase's demo script; the site is one design task.

The pattern across all ten: agent throughput rises sharply once the contract for that phase exists, and is close to zero before it. Phases 3 and 5 are where the leverage is largest, which is another reason not to compress phase 3 — a rushed contract does not just cost you later, it removes your ability to parallelise at all.

8 · Decisions an agent never makes

  • Schema and API shape. Adding a manifest field or renaming an endpoint changes a contract four other agents are building against. Escalate, always.
  • Security posture. Token handling, the capability model, the Host and Origin checks, what the approval screen shows. These are the places where a plausible simplification is a real vulnerability.
  • Licensing. The ffmpeg build, any new dependency's licence. A dependency diff in the gate exists precisely to surface this.
  • Deleting or weakening a test. If a test is wrong, that is a finding, not an edit.
  • Anything destructive on your machine. No agent deletes weights, touches the models directory, or runs reclaim. The one-way operations stay manual.
  • Design judgement. Copy, hierarchy, what a screen is for. An agent implements the frozen design; it does not revise it.

10 · Cadence and mechanics

Worktrees, not branches on one checkout. Each implementer gets an isolated copy so two agents editing adjacent files never collide. Cheap to create, discarded if unchanged.

Batch by gate, not by agent. Let three or four finish, run the gate once across all of them, then review the ones that passed. Reviewing a diff that has not passed rung 5 is wasted attention.

One integration window a day on your Mac, late enough that a day of cloud work has accumulated. Anything machine-bound queues for it. Keep that window sacred — it is the only place the product is actually proven to work.

The decision log is the shared memory. Agents have no continuity between runs, so whatever is not written down is re-decided, differently, every time. One append-only file with the date, the decision and the reason, handed into every brief, is what keeps twelve independent runs coherent.

Where this stops helping

Agent throughput does not compress phases 1 and 7, because the walking skeleton is one indivisible thing and ffmpeg correctness is empirical work on real files. Expect the sixteen weeks to become perhaps ten or eleven rather than four — the gain is real and it is concentrated in phases 0, 3, 5, 6 and 9, which happen to be the phases with the clearest contracts. That correlation is not a coincidence; it is the whole thesis.

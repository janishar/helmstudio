Milestones and review protocol

Eleven milestones for one implementer working sequentially, with a review at each boundary. h3 studio is the reference implementation and is already complete — it is the target the framework is built against, not something to be built.

Sonnet 5 · implementer Opus 5 · reviewer Review at boundaries only Nothing runs until you say so

Two agents, two jobs

Impl

Sonnet 5

Builds one milestone against contracts that already exist, in files it is told it may touch. Runs the gate itself before reporting. Produces a branch and a report, never a merge. Stops and escalates rather than improvising when the design is inconsistent.

Review

Opus 5

Reads the diff, the milestone document and the named design sections. Produces ranked findings and changes nothing. Judgement work — contradictions with the frozen design, missed edge cases, the failure nobody wrote a test for.

The model split follows the work: bounded implementation against a written contract is where Sonnet is strong and cheap enough to iterate, while review is the judgement-heavy end where a stronger model earns its cost — a reviewer that misses a contradiction costs far more than the tokens saved. Keeping the roles in separate runs is what stops an implementer quietly relaxing a test to make itself pass.

The prerequisite before any run

The frozen design has to live in the repo

It is currently in published artifacts, which an agent in a container cannot read. Before M0 starts, the eight design documents are exported to docs/design/*.md in the helmstudio repository. From then on that directory is the contract every brief points at, it is version-controlled alongside the code it describes, and a design change is a pull request like anything else.

This is not busywork. An agent that cannot read the design will infer it from the code, which inverts the whole arrangement — the code becomes the spec and the documents become decoration. It is the first task in M0 for that reason.

Standing implementer brief

Prepended to every milestone run. The milestone document supplies the rest.

ROLE You implement one milestone of helmstudio. You do not design it. READ docs/design/** — the frozen design. It is the contract. docs/decisions.md — every decision made so far, with reasons. The milestone document you were given. Read all three before writing code. RULES Touch only the files the milestone names. Do not edit tests you did not write. Do not change a schema, an API shape, or a token name. Do not add a dependency without saying so in your report. Do not weaken or delete a failing test — that is a finding, not a fix. VERIFY Run the gate yourself before reporting. A milestone is not done because the code is written; it is done when the gate is green. ESCALATE If the design is inconsistent, ambiguous, or wrong: STOP. Report the contradiction with a quote from docs/design, say what you would do and why, and wait. Do not resolve it yourself — four other decisions depend on it being resolved once. REPORT What you built · gate output · what you could not verify and why · every judgement call you made · anything you noticed but did not touch. Append one line per decision to docs/decisions.md.

Standing reviewer brief

ROLE You review one completed milestone. You change nothing. INPUT The full diff · the milestone document · docs/design/** · docs/decisions.md · the implementer's report. LOOK FOR in this order of value: 1. Contradictions with the frozen design — quote both sides. 2. Things the definition of done passes but a user would hit: the failure path nobody tested, the state with no UI, the error that surfaces as a stack trace. 3. Decisions made silently that should have been escalated. 4. Tests that assert the implementation rather than the contract. 5. Scope creep — anything outside the milestone's TOUCH list. 6. Only then: correctness, clarity, dead code. OUTPUT Ranked findings. For each: BLOCKING or SHOULD-FIX or NOTE, the file and line, what is wrong, and the concrete fix. Say plainly if the milestone is done. Do not pad with praise. DO NOT Edit any file. Re-litigate frozen design decisions — if you think one is wrong, say so once as a NOTE and move on.

The gate, once

Every milestone's definition of done is the same command plus its own specifics. Build this in M1 so that everything afterwards can use it.

make gate ✓ gofmt · go vet · dependency diff clean ✓ go test ./... (macOS and Linux) ✓ helm validate studios/*.yaml ✓ generated clients regenerate with no diff # from M4 ✓ conformance: daemon + embedded # from M4 ✓ visual regression, both themes # from M6

Anything the gate cannot check happens in your integration window on the Mac. Each milestone lists those items explicitly so they queue rather than getting lost.

M0 · Contracts

M0

Nothing runs, everything is written down

2–3 days

Scope

  • Export the eight frozen design documents to docs/design/*.md; create docs/decisions.md seeded with the decisions already made.
  • Write schema/manifest.json — the full JSON Schema including processes[], runtime, weights[] with selectable, storage, capabilities, sdk, test, network.
  • Write helmstudio.yaml for all four studios by reading the real repositories. h3 studio first — it is complete and known, so it is the calibration case.
  • cmd/helm/validate.go — the validator, as a standalone binary.
  • api/openapi.yaml — endpoint names and request/response shapes only. No schemas yet.

Definition of done

helm validate studios/*.yaml → 4 valid, 0 errors helm validate test/fixtures/bad-*.yaml → each rejected, naming the field go test ./... · gofmt · go vet → clean
Review focus
  • Does any of the four manifests need a field that exists only for it? That is a schema smell and the whole point of this milestone.
  • Does any manifest paper over a gap with a shell one-liner that the schema should express?
  • Are runtime.framework and backends correct per studio — native-kernel/metal for h3 and iris, mlx/metal for ltx, pytorch/mps for AuK?
  • Is h3's health timeout 30 s, not 240? The dry run established that its server is a thin wrapper.
Machine-bound

Nothing. This milestone runs entirely in the cloud, which is why it is first.

M1 · Foundation

M1

Repo, platform seams, store, gate

5–6 days

Scope

  • Monorepo skeleton: cmd/helmstudio, cmd/helm, internal/…, packages/ placeholders.
  • internal/platform — the four seams as interfaces with darwin implementations only: process group control, secret store, app paths, reveal in file manager.
  • Directories helper: four roots resolved per OS, HELMSTUDIO_HOME and per-root overrides, library defaulting to ~/helmstudio, adoption of an existing ~/.helmstudio.
  • internal/store: SQLite open with the four pragmas, migration runner on user_version, schema v1 — installations, step_runs, processes, jobs, log_files, settings.
  • make gate and the CI workflow, running on macOS and Linux.

Definition of done

make gate → green on macOS and Linux go test ./internal/store/... → migrations up from empty, idempotent, refuses a higher user_version HELMSTUDIO_HOME=/tmp/x helmstudio --print-paths → all roots under /tmp/x
Review focus
  • Are foreign_keys(ON) and WAL actually set, and proven by a test rather than asserted in a comment?
  • Is the write connection capped at one, with a separate read pool?
  • Does any path escape the directories helper? Grep for string concatenation with a home directory.
  • Do the platform interfaces have a shape a Windows implementation could satisfy, or do they leak POSIX assumptions into their signatures?
Machine-bound

Confirm the Keychain implementation stores and retrieves a token on your Mac. Everything else is cloud-verifiable.

M2 · Supervision

M2

The walking skeleton, proven against h3 studio

7–8 days

Scope

  • Manifest loader with three-source resolution; local_path path for now.
  • Port allocator over the configured range, with a net.Listen probe.
  • Template substitution: {port}, {ports.x}, {models.x}, {root}, {data}, {venv}.
  • Supervisor: spawn with Setpgid, dependency-ordered group start, health polling against the declared budget, reverse teardown with SIGTERM then SIGKILL, and re-adoption verifying pid, start time and pgid.
  • Log files with an index row, streamed over SSE; retention of the last five per studio.
  • A deliberately plain HTML shelf: list, Launch, Stop, live state. No design system.

Definition of done

go test ./internal/supervisor/... → group ordering, health timeout, teardown order, re-adoption identity check, all against fake child processes make gate → green
Review focus
  • Is the re-adoption check all three of pid, start time and pgid? Two is a bug that surfaces as killing an unrelated process months later.
  • Does a failed health check ever trigger a restart of a main process? It must not — an eight-minute generation has to survive a slow probe.
  • Is teardown genuinely reverse-dependency-ordered, and does it kill the group rather than the process?
  • Does a startup sweep mark an interrupted step interrupted rather than failed? The distinction changes what Retry does.
Machine-bound · the M2 demo

Launch h3 studio from a local checkout, generate a video, kill -9 the daemon, restart it, confirm re-adoption. Then stop and confirm no process survives. Needs h3's /healthz merged first.

M3 · Install and weights

M3

From a URL to a ready studio

8–9 days

Scope

  • Clone with submodules at a pinned ref; ordered build steps with streamed output; resume from the first non-succeeded step; cancel by process-group kill.
  • Tool probing from requires.tools, failing with the command that installs the missing one.
  • Hugging Face downloader: listing, range resume from .part length, URL re-resolution on every resume, 429 backoff, auth_required on 401/403, token from the platform secret store.
  • Linked weights: point at an existing directory, symlink into the cache, read-only, missing when the target goes.
  • Disk pre-check; the cache view with reference counts; reclaim that never follows a symlink.

Definition of done

go test ./internal/install/... ./internal/weights/... → resume from a truncated .part, 403-on-resume re-resolves, 429 backs off, reclaim refuses a linked artifact, build resumes at the failed step make gate → green
Review focus
  • Can any delete path follow a symlink? This is the finding that matters most in this milestone — deleting a user's own 60 GB checkpoint is unrecoverable.
  • Is a 403 on resume treated as an expired URL rather than corruption?
  • Are weights passed as absolute paths, with nothing symlinked into the studio checkout?
  • Does a partially complete linked directory get written into, anywhere?
Machine-bound · the M3 demo

Clean install of h3 studio end to end, interrupted once mid-build and resumed. Then install again against a model directory you already have and watch nothing download.

M4 · Platform API and SDK

M4

The contract everything else lives on

10–12 days

The most consequential milestone, and the one to review hardest. Consider splitting the review: once when api/openapi.yaml is complete and before any implementation, then again at the end.

Scope

  • Complete api/openapi.yaml. Schema v2: sessions, kv, records, assets, derived, items, item_inputs, tags, items_fts, inbox.
  • Endpoints in order: /me, /kv, /sessions, /assets and :adopt, /gallery, /records, /jobs, /events, /handoff.
  • Capability-scoped per-launch tokens injected at spawn.
  • Media engine v1: probe, thumbnail, poster, waveform, h264 proxy as derived files.
  • Generated Go and Python clients; the embedded provider; helm dev; helmstudio fsck.
  • The conformance suite, written from the OpenAPI document and run against both providers.

Definition of done

make gate → now including client drift and conformance × 2 conformance: identical results, daemon and embedded helm dev --fixtures → a studio runs with no daemon installed
Review focus
  • Was the conformance suite written from the contract or from the implementation? Check whether it would catch a deliberate bug.
  • Does :adopt hardlink, never copy? A copy is a silent performance cliff at 2 GB.
  • Is dedup a uniqueness constraint rather than an algorithm, and is there any stored reference count that could drift?
  • Can a studio's token reach another studio's namespace under any endpoint?
  • Does the records filter language accept anything that reaches SQL unparameterised?
Machine-bound · the M4 demo

h3 studio records real takes through the SDK; thumbnails and provenance appear; an image handed to h3 as a first frame produces a lineage row.

M5 · The Python studios

M5

ltx studio and AuK studio — the second caller

6–7 days

Per-studio uv environments pinned to python.version; the Python runtime SDK against a real caller; the one-heavy-studio rule with the switch dialog, now that two studios genuinely compete for memory. Expect schema churn and treat it as the milestone working — this is what tells you which parts of M0 were guesses.

Review focus
  • Any special case in Go for a specific studio. If one appears, the schema is wrong and the fix belongs in the schema.
  • Are the two environments genuinely independent — no shared site-packages, no shared interpreter?
Machine-bound

Three studios installed side by side; AuK generating speech into the shared gallery; a switch from ltx to h3 showing real memory arithmetic.

M6 · Design system and UI

M6

helm-css, the real launcher, helm-ui-sdk

10–12 days

The five CSS layers with visual regression and a contrast check on every token pair; the fourteen screens from the design document; then helm-terminal, helm-gallery, helm-player in that order. Theme pushed over SSE so toggling the launcher re-themes running studios. The h3 token migration — 45 variables mapped, 64 literals cleared — belongs here as a separate task against h3's repo.

Review focus
  • Every state in the canonical vocabulary has a chip, including the failure states.
  • No colour defined only inside a media query or [data-theme] block.
  • Does helm-terminal virtualise? Thirty lines a second will find out in production otherwise.
  • Do components receive a client rather than constructing one?

M7 · Library, editor and iris

M7

Anyone can add a studio

6–8 days

iris studio with selectable weights and the checkpoint picker; the three-source manifest library with local override and Revert; the in-app editor with live validation and criteria scoring; import from file, paste and URL, and export; the certification checks and the approval screen with every build command shown verbatim.

Review focus
  • Is import genuinely not install, in the code as well as the copy?
  • Does the approval screen show the commands verbatim, unelided, before anything executes?
  • Does an id collision ever resolve silently?

M8 · Timeline and export

M8

The one that will be wrong twice

10–12 days

Timeline document and rows; the editor component; export as a Job with the conform-to-target filter graph and the stream-copy fast path; golden frame-hash tests across both providers. Settle the ffmpeg licensing question before this starts, not during.

Review focus
  • Is the stream-copy path taken only when genuinely legal — same codec, resolution, fps, audio parameters, no transitions, no gain?
  • Do golden tests actually compare frame hashes, or just that a file was produced?
  • Does a timeline's clip count as a reference for reclaim?
Machine-bound · most of it

Export correctness cannot be judged in a container. Budget real time in your integration window for this milestone specifically.

M9 · Mac app and release

M9

Something a stranger can install

7–9 days

Electron shell with the stdout handshake, daemon adoption, quit behaviour and the menu-bar option; native affordances; browser-path auth with the one-time token URL, SameSite=Strict cookie and the Host and Origin checks; signing, notarisation of the bundle and the nested binary, the update feed and the Homebrew formula.

Review focus
  • Does the renderer ever see the token?
  • Is navigation locked to loopback, with external links handed to the system browser?
  • Are the CSRF defences present on every mutating endpoint, not just the obvious ones?
Machine-bound · all of it

Signing and notarisation need your certificates and cannot be delegated.

M10 · Documentation and the site

M10

Assembly, if the tracks were kept

8–10 days

The SDK documentation — quickstart, concepts, guides, generated API and manifest reference, CLI reference, publishing criteria, and the four annotated launch manifests. Then helmstudio.in. Both built with helm-css, reference pages regenerated in CI.

Review focus
  • Is any reference page hand-written? It must be generated or it will drift.
  • Does the quickstart run, verbatim, on a clean machine?

A note on depth

M0 through M4 are specified; M5 onward are scoped

That is deliberate rather than unfinished. M5's shape depends on what M0's manifests reveal, M6's on what the API actually looks like, M8's on how the media engine behaves in practice. Writing them in full today would produce documents that get rewritten before anyone reads them. Each is expanded to M0-level detail at its own kickoff, by which point the two things a good brief needs — the contract it builds against and the last milestone's findings — both exist.

The same applies to the review checklists. The ones above are what is knowable now; each will gain items from the previous milestone's findings, which is how a review protocol should accumulate rather than being guessed at the start.
